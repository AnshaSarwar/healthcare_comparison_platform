### Phase 2 — Auth Follow-ups

- **Email verification**: `POST /auth/register` now creates users with `email_verified=false` and fires a verification email; `POST /auth/email/verify` and `POST /auth/email/resend-verification` (always 202, no user enumeration) complete the loop. Non-blocking by design — `/auth/me` exposes `email_verified` for the frontend to nag on, but an unverified user can still log in. Seeded demo users are pre-verified.
- **Password reset**: `POST /auth/password-reset/request` (always 202) + `POST /auth/password-reset/confirm` (30 min, single-use token). Confirming a reset revokes every existing refresh token for that user — treated as compromise recovery, forces re-login everywhere.
- **Invite-based provider onboarding**: healthcare providers can no longer self-register (`POST /auth/register` now rejects `org_type=healthcare_provider`). A platform admin creates an invite (`POST /invites`), the invitee previews it publicly (`GET /auth/invites/{token}`) and accepts (`POST /auth/invites/{token}/accept`), which creates the org + `HealthcareProvider` profile + pre-verified `healthcare_org_admin` user and logs them in. `GET /invites` / `POST /invites/{id}/revoke` manage them from the platform-admin side.
- New `backend/core/email.py`: console-logs in dev by default (no SMTP provider in `infra/docker-compose.yml`), or real SMTP via stdlib `smtplib` (`EMAIL_BACKEND=smtp`) — deliberately no vendor SDK, same "don't pick a SaaS vendor yet" posture as the Stripe/billing gap.
- New `backend/services/auth_flows.py` holds token issuance/consumption for all three flows, kept separate from tenant CRUD in `backend/services/admin.py`.
- New tables via `alembic/versions/0007_auth_followups.py`: `email_verification_tokens`, `password_reset_tokens`, `provider_invites`, plus `users.email_verified`. Applied manually to the local dev DB (`ALTER TABLE ... ADD COLUMN`) since this DB tracks `create_all`, not `alembic upgrade head` (confirmed `alembic current` was still pinned at `0001_initial` even though tables through migration `0006` already existed — local dev has never actually run `alembic upgrade head`, only `create_all`).
- Rate limits added for all new public endpoints (`rate_limit_verify_email`, `rate_limit_resend_verification`, `rate_limit_password_reset_request`, `rate_limit_password_reset_confirm`, `rate_limit_invite_accept`).
- 21 new tests in `tests/test_auth_flows.py` (pure logic + auth-shape checks, no live DB needed, matching the existing suite's style); full suite at 84/84, ruff clean.
- **Bug caught during live smoke-testing** (register → verify → reset → invite-accept, all exercised against real Postgres): four new endpoints 500'd because slowapi's `headers_enabled=True` needs a `response: Response` parameter declared to inject rate-limit headers into, or it raises — the exact gotcha already documented in `rate_limit.py`'s docstring for the *existing* routes, which I missed on the new ones first pass. Fixed and reverified live.
- Also fixed a latent, unrelated-to-the-task visibility bug in the new console email backend: it originally logged at `INFO`, which is silently dropped since this app has no root logging config anywhere (confirmed other pre-existing `logger.info` calls, e.g. the indexing-queue "Enqueued N documents" log, never appear either) — switched to `logger.warning` so the token is actually visible in dev.
- Cleaned up all test users/orgs/invites created during live smoke-testing from the dev DB afterward.

### Phase 3 — Generated TypeScript Client

- Checked whether the schema-fetch step needed a live server: `app.openapi()` only
  introspects routes/Pydantic models and every `Settings` field already has a default, so
  importing `backend.main.app` and dumping the schema needs no DB/Redis/Qdrant — no live
  server, no `docker compose up`, in either local dev or CI. Went with that (a static
  `openapi.json` export) over spinning up a live server.
- Audited every endpoint the frontend calls for a missing `response_model` first, per the
  task: all JSON-returning ones already had one. The only gaps were the two SSE streams
  (`/agents/chat`, `/rag/query`, no `response_model` by design) and the raw-bytes
  `/documents/{id}/content` download — none of which the frontend treats as typed JSON
  anyway, so no backend changes needed there.
- Added `scripts/export_openapi.py` (imports `backend.main.app`, writes `openapi.json` to
  repo root, gitignored) and `frontend`'s `generate:types` npm script
  (`python ../scripts/export_openapi.py && openapi-typescript ../openapi.json -o
  src/lib/generated-types.ts`); `openapi-typescript@^7.13.0` added as a frontend
  devDependency. `generated-types.ts` itself **is** committed (it's the artifact the
  frontend build actually needs; only the intermediate `openapi.json` is gitignored).
- Rewrote `frontend/src/lib/types.ts` to re-export/wrap `generated-types.ts` instead of
  hand-declaring backend-mirrored shapes. Kept hand-written: `AgentSseEvent`/
  `SourceChunk`/`AgentChatFinal` (no `response_model` to derive from — the SSE routes
  aren't in the schema at all) and two deliberate narrowings over what the backend
  under-types — `ProviderInvite.status` (plain `str` in the backend schema; DB check
  constraint, not a Pydantic enum) and `PlanVersion.extraction_metadata` (untyped `dict`,
  like `raw_terms`).
- Updated `frontend/src/lib/api.ts` to use the generated `*CreateRequest`/
  `*UpdateRequest`/`*Read` schema types for request bodies and responses instead of the
  old hand-typed inline shapes (`PlanCreateRequest`, `PlanUpdateRequest`,
  `HospitalCreateRequest`, `EmployerUpdateRequest`, `OrganizationCreateRequest`,
  `UserCreateRequest`, `RegisterRequest`, `LoginRequest`, `TokenResponse`, and the various
  auth-flow request schemas) — verified each request schema's actual field names against
  the exported `openapi.json` before swapping (e.g. `PasswordResetConfirmRequest.new_password`,
  `ComparisonCreateRequest.plan_ids`) rather than assuming they matched.
- **Bug caught by the stricter generated types, not previously known:** `PlanVersionRead`
  (`backend/schemas/policy.py`) never declared `extraction_metadata`, even though the
  `PlanVersion` ORM model has always had that column (`backend/models/entities.py`) and
  `frontend/src/app/(app)/provider/page.tsx`'s "Review terms" panel has always read
  `version.extraction_metadata.evidence` off the API response. Runtime effect: opening
  that panel on any real plan version would throw (`Cannot read properties of undefined`)
  — the hand-written frontend type had just been silently asserting the field existed.
  Fixed by adding `extraction_metadata: dict` to `PlanVersionRead` (all three endpoints
  that return it use `model_validate(version)` with `from_attributes=True`, so no service
  code changes were needed) — the same category of fix as auditing `response_model`
  completeness, just one level deeper (a field missing from an existing `response_model`
  rather than a whole missing `response_model`).
- Also fixed two more `tsc` failures the stricter generated types surfaced (both pre-existing,
  unrelated to the endpoint audit): `platform/page.tsx`'s `userRole` state was untyped
  `string` instead of `UserRole` (same pattern already used for `orgType` one line above —
  just never applied to the role field), and `comparisons/[id]/page.tsx` treated
  `ComparisonResultRead.citations` as always-present when the backend schema (correctly)
  has it optional with a default.
- Added a CI step (frontend job, `.github/workflows/ci.yml`) between lint and typecheck:
  installs backend deps, reruns `generate:types`, and fails the build on
  `git diff --exit-code -- src/lib/generated-types.ts` if the committed file is stale.
- Verification: `tsc --noEmit` and `eslint` both clean after the fixes above; full backend
  suite 84/84, ruff clean. Attempted a live round-trip smoke test (create a plan version
  with `extraction_metadata`, then read it back) but hit unrelated pre-existing local dev
  DB drift — `plan_versions` in the actual Postgres instance is missing a `coverage_type`
  column entirely, so both the insert and a plain `SELECT` on that table 500 regardless of
  this change (same "local dev has never run `alembic upgrade head`" issue noted in the
  Phase 2 entry above, now confirmed to affect `plan_versions` specifically, not just the
  new auth tables). Didn't touch the dev DB to work around it — out of scope for this
  task. Confirmed correctness instead via the full test suite, the OpenAPI schema
  reflecting the new field correctly, and the identical `from_attributes` mechanism
  already working for `raw_terms`/`normalized_terms`.
- `CLAUDE.md`: removed the "no generated TypeScript client" known-gap line, added a new
  bullet under Architectural boundaries documenting the generate/CI-check workflow.
